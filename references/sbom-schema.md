# SBOM Schema

## Purpose

> **Scope:** The report-table schema for the per-project Software Bill of Materials section
> **Key items:** column contract, license and advisory fields, completeness touchstone,
> source-derived disclaimer

This file defines the table shape of the Software Bill of Materials section in
`process/report-format.md`. The extraction procedures that fill the table live in
`references/dependency-manifests.md`, and the license classification rules live in
`references/license-compliance.md`. This file defines only what the report renders.

Apply `principles/evaluation-rules.md` throughout.

## What The Section Is And Is Not

The SBOM section is a lightweight source-derived component table. It is not a claim of SPDX or
CycloneDX format conformance, it is not generated by an SBOM tool, and it is not evidence about
the contents of a shipped artifact. The section opens with a one-line statement making this
distinction explicit, matching the labeling rule in `references/dependency-manifests.md`.

The inventory reflects the manifests at the audited revision. A lockfile entry proves resolution
intent, not what a released binary or container contains.

## Table Schema

| Column           | Content                                                                            |
|------------------|------------------------------------------------------------------------------------|
| Component        | Package or component name as declared                                              |
| Version          | Resolved or declared version, `UNKNOWN` when not derivable                         |
| Ecosystem        | `purl` type per `references/dependency-manifests.md`, for example `npm` or `cargo` |
| Relationship     | `direct` or `transitive`, where derivable, else `UNKNOWN`                          |
| License          | Declared license from an inspected source, else `Unknown`                          |
| License Risk     | `None flagged`, `Review`, `Conflict`, or `Unknown` per the license checklist       |
| Advisory Checked | `Y` only when a committed advisory or scan artifact covers the component, else `N` |
| Source File      | The manifest or lockfile the entry was read from                                   |

## Rules

- Populate `License` only from inspected declarations: a `license` field in the manifest, a
  vendored `LICENSE` or `NOTICE` file inside the component, or a lockfile license field where the
  format carries one. Registry knowledge and typical-license guesses are not evidence, mark
  `Unknown` instead.
- `License Risk` follows `references/license-compliance.md`: `Conflict` for a
  copyleft-versus-distribution clash, `Review` for licenses needing legal attention, `Unknown`
  when the license itself is unknown, `None flagged` otherwise.
- `Advisory Checked` stays `N` for every component unless committed vulnerability or scan output
  supplies `Reported` evidence for it. Naming an advisory database is not checking it.
- `Unknown` licenses are expected, most manifest formats do not declare dependency licenses. A
  high `Unknown` count is itself a license-compliance finding input, not a table defect.
- Count direct and transitive components separately and report both totals under the table.
- Cap a long table: show direct components in full, summarize transitive components by count and
  notable entries, and record full totals in the evidence ledger.
- Record every manifest and lockfile read as an `Inspected` evidence row.

## Completeness Touchstone

Use the current CISA Minimum Elements for an SBOM as a completeness reference when judging how
much of a real SBOM the table approximates. The 2026 edition makes Component License a minimum
element, which is why `Unknown` license cells are surfaced rather than silently omitted.

Do not state or imply the table satisfies those elements. It approximates an inventory subset and
states that fact.
